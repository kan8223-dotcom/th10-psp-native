## 1. Go の枠
- **ユーザー領域**: MEMSIZE=1＋ARK-5 の Extra Memory=Max が前提。SDK 上の最大は 55MiB で、partition 11 を使う構成だと 51MiB（T7）。予算表 B§1 は「約56MiB」と書いている。
- **起動宣言**: 妖々夢と同じ PSP_HEAP_SIZE_KB(-2048)（L239 L29）。起動直後にカーネル側へ残る空きは 761,856B（L239 L32）。
  - sceKernelTotal/MaxFreeMemSize が返すのはヒープの外の残りなので、ヒープの余裕判定には使えない（T7）。
- **ヒープ上限（実測）**: r147 で arena が 44,601,088B から伸びなくなり、ECL の 51,248B が確保できなかった（L147 L236-449、台帳 L284）。このときの ELF は約 9.5MiB。
  - 上限は ELF サイズと 1:1 で連動する。
  - 予算表の「heap_arena 47.2MiB」は実機ログで確認できなかった。数字の食い違いとして併記する。
- **r238 系の 6B 開始時**（L239 L292、L253 L212）
  - 確保済み（sbrk 済み）38.1〜38.2MB、使用中 約37.9MB、空き 0.27〜0.35MB、最大連続 0.18〜0.24MB。
  - 上限（44.6MB）との差の約6MB はまだ確保していない余地、と推定している。
- **r238 の常駐 約48.6MiB**（B§2.2〜2.4、M8 L14）

  | ELF | 9.47MiB | text 5.12＋bss 4.32 |
  | stage pool | 13.51MiB | Enemy 7.71／Bullet 4.50／Item 1.55／Laser 0.37MB |

- **volatile 4MiB**: Go の r238 は使っていない（B§1）。1000 では ANM scratch をここに置き、実機でロックが取れた（M8 L37）。
- **(a) GE VRAM**
  - **永夜抄 Go は sceGeEdramSetSize を呼んでいる**: ge4wrap_texv1.prx のカーネルスタブ経由（T7 psp/ge4_game_kernel/src/ge.S L8・main.c L31）。TH08 の ge4_bridge.cpp は L464 で 4MiB に広げ、L338 で終了時に 2MiB へ戻す。実機ログでも見えている量は 4194304（L239 L75）。
  - **下位 2MiB**: 表示 278,528×2 と深度 278,528 で、残りは 1,261,568（L239 L84）。
    - r238 はボス立ち絵の本体だけを下位へ置く。例: face_st05.anm 262,144B（空き 1,064,960→802,816。go-r239-20260921/BOOT.go-r239T-lite-sc-demo-423-20260921.LOG L336）。
  - **上位 2MiB**: 3枚目の表示バッファ 278,528（0x04200000）と、頻繁に使うテクスチャの昇格先。r238 のレシピは GE4_HOT_TEXTURES=1 で昇格を有効にしている。
    - ログ上のピークは 2,048,000B。昇格は 70 回中 22 回成功、48 回は容量不足で Main RAM に残った（L239 L1733）。
  - **以前のメモ「2048KB 中 1360KB・SetSize 未使用」は、記録では TH06 の Go ログの値**:
    - TH06 の Go 実機ログに「EDRAM SIZE 2048KB USED 1360KB FREE 688KB」「SETSIZE NONE」とある。
    - 永夜抄の記録とは食い違うので、両方を併記する。
  - **1000 レーン**: GE4 を無効にしている。上位 2MiB が無いため（B§9.3）。
  - **妖々夢**: 上位を立ち絵キャッシュに使った。
    - 設計は自機 512K＋ボム 512K＋面4枠×128K で計1536K、実測ピークは 1408K、fallback 0（T7）。
    - Go では最初は機種ゲートで Main RAM に逃がしていたが（M7 L43）、後で開放した（M7 L159）。
- **(b) ME eDRAM**
  - **容量**
    - 1000 は 2MiB（Hot Chips 16）。
    - Slim 以降の 4MiB は m-c/d 説（未確定）。ただし 3000 では 0x200000-0x25ffff のリングと 0x3f0000-0x3fffff のスタックガードを実際に使っている（T7 docs/MECC_BGM_384K_INTEGRATION.md L10-11、L35-40）。
    - Go の容量は記録なし。
  - **化けの実測**（すべて 3000 実機1台。メイン CPU 側で CRC を取った値。同じ場所が同じように化け、キャッシュ経由かどうかに関係しない）

    | 置き場所 | 滞留時間 | 化けたブロック | 出典 |
    |---|---|---|---|
    | 上位 2MiB | 約12秒 | 26,928/29,554＝91%（別記で 56〜91%） | M7 L21 |
    | 上位 384KiB | 約2.2秒 | 651/23,928＝2.7% | M7 L26 |
    | 上位 384KiB（別の走行） | 約2.2秒 | 322/14,922＝2.16% | T7 |
    | 下位 384KiB（0x10000-0x6ffff、R18C） | ポーズ込み | 79/2,157＝3.66% | 同 L46-52 |

    - **0.5秒や1秒の滞留を測った記録は無い**。
    - RID25 の seed を1フレームだけ置いた試験（65,728B）は正しさ 4/4 合格のベンチで、リテンションを測ったものではない（M7 L61）。
  - **音声での使用**
    - 3000 の MECC は、2MiB → 384KiB → 下位384KiB と移して、最後は 0（M7 L132、T7）。
    - 1000 の MIST は BGM リング 393,216B を eDRAM に置き、Main RAM を正味 393,088B 空けた（T7 README L37-41、CREDITS L20-25）。1000 で CRC やノイズを評価した記録は無い。
    - 永夜抄の r249 以降は edram=0（L253 L17）。
  - **運用ルール**（M7 L96）: 1秒以内に書き直すものだけを置く／止まるときは全部捨てる／正本は Main RAM に置く。
  - **GE 上位の長時間滞留は未検証**: 検証は要求されたが、やった記録が無い（T7）。
    - 妖々夢 Go@443 で出た画面全体の帯状破損は、立ち絵（上位）と OC のどちらが原因か切り分けられないまま決着していない。

## 2. 効いた手
- **stage pool の遅延確保**（すべて frame-exact を確認済み）
  - ECL コールスタック −3,682,304B（B§8.2）
  - チャンク 256→32 で −495,616B（B§8.5）
  - trail −1,204,224B（M8 L227）
  - secondaryVms −450,048B（B§26）
  - CompactAnmVm（描画専用の行列を除去）−1,662,976B（B§16）
- **頂点バッファ 0x18000→0x4800**: −2.24MB。実測のピークは 5,744 頂点（B§8.7）。
- **ELF 9.47→6.71MiB**: ME 用 BSS −1.18、gc-sections −0.29、HarfBuzz を外した SDL_ttf（B§7、§8.4）。
- **起動時の一時使用**: 自己チェックサムを 64KiB ずつの流し読みにして、一時的な 5.4MB が不要になった。SE 複製の共有で ≥1.6MiB（推定）（B§8.10）。
- **ANM scratch 8.25→3.2MB**: 収まらない ANM は空いている stage pool に一時展開する。1面開始時の空きが 289KB→977KB、さらに約4.8MB 伸ばせる（PPSSPP、台帳 L286）。Go 実機でも title01 の 7,386,448B を pool に置いている（L239 L134）。
- **テクスチャ 16bit 化＋best-fit＋LZSS を 64KiB 単位で読む**: これで Go で初めて最後まで通った（M8 L136-137）。
- **CLUT8 減色（1000）**: GE 待ちはほぼ 0（B§30.3）。
- **動的テキストのその場更新（1000）**: CLUT8 で固定確保し、glTexSubImage2D で上書きする。「最大連続 65,472」止まりの断片化が消えて 6B を完走（B§30.2）。
- **1000 モデルでの全面完走**: 裏バッファの遅延確保（614,400B）、ロード画面の凍結フレーム省略（−512KB）、エフェクトの圧縮、surface の画素を volatile に移す（M8 L237）。
  - volatile の余り 960KB に GE 用の 557,056B を置き、stream lease の失敗 25% を 0 にした（B§25）。
- **大きな ANM の展開**: 展開元を描画アリーナに置き、使い終わった前方から解放する。title01 の 7.4MB でピーク約8MB（B§9.4）。
- **ログを RAM にためる**（128KiB、Go は 768KB）: 面の途中でメモステに書き込まなくなった（M8 L187、L362）。

## 3. 罠と失敗
- **断片化**
  - face_yk00 の 1.58MB が、空き 10.2MiB あっても取れない（M8 L51）。
  - ECL 51KB（L147）、face_st06 の 1MB（M8 L136）。
  - 動的テキストを作り直すたびに 65,472B の使えない断片が残る（B§30.2）。
- **16bit が取れないと 32bit に落ち、倍の連続領域を要求して NEW_FAIL→TERMINATE**（B§27、§25）。最終的な対策は 16×16 の透明テクスチャで続行すること（M8 L250）。
- **operator new が失敗すると std::terminate で XMB に戻り、ログが消える**（R-057、M8 L134）。
- **依頼文の訂正: 遅かったのは DXT だけ**。GE 待ちが 8.5〜14.1ms/フレーム。DXT を全部やめると 16.9ms/フレーム、GE 待ち 0.02ms（B§29）。CLUT8 はフル速度。
- **「会話時だけ立ち絵を読む」は不成立**
  - Spellcard::Init がボム用のカットインに立ち絵を使う（B§9.3）。
  - 6B と EX の顔を会話専用と思い込んで捨てたら、カットインが NULL を参照して落ちた（M8 L248）。
- **CompactAnmVm で memset のサイズがリテラルのまま**: 縮んだ構造体の後ろにある BSS を潰していた。該当 5箇所（M8 L221）。
- **ME の dcache**
  - 妖々夢の Item-ME は 4 連敗。uncached 別名で読むようにして解決（M7 L64-66）。
  - 永夜抄のポップアップも同じく uncached 別名にした（M8 L177）。
- **ef0 の 30秒停止**
  - 前触れは FreeType の seek/seek/極小 read の連打。
  - 4KiB キャッシュを挟んでも、seek と read の連打が続くと再発した。
  - Go だけフォントを常駐させて解決（754KB）。
  - LZSS の 4KiB 単位の読み込み連打でも起きる（M8 L136）。
- **ビルドフラグの配線漏れ**
  - Makefile に -D の変換と #include が無いと、#if の中身が丸ごと消えても exit 0 で終わる（M8 L194）。
  - include が GO_IO_LAMP のブロック内にあった（B§7）。
  - ビルドスクリプトが第2引数を捨てていた（M8 L183）。
  - 既定値が REPLAY_SYNC_AUDIT ?= 1 になっていた（M8 L113）。
- **計測の罠**
  - PPSSPP の arena は上限ではない（M8 L218）。
  - Go 版を PPSSPP で確認するときは PSPModel=1 にする。0 だと title01 で偽のクラッシュになる（M8 L375）。
  - 3000 で MEMSIZE=1 が 1回目だけ効かなかった（B§29）。
  - 800200D9 は high memory の設定漏れ（M7 L68）。
  - Go で high memory を有効にすると ARK が Pause を無効化する（T7 docs/ARK5_HIGH_MEMORY.md L54）。

## 5. Android（Adreno 205）
- **uniform 分岐のシェーダをやめて、状態ごとの変異シェーダにする**
  - TH08 は uniform で分岐するシェーダ1本で、四角形1枚に約66ms かかっていた。変異シェーダにしてタイトルが 15→59fps（MX 09-28）。
  - TH06 は 12変異で 38→52〜58fps（A§8）。
  - TH10 の上流も uniform 分岐なので、変異シェーダは必須。
- **描画ごとの glBufferData をやめる**（A§7）。
- **バッファを3枚に**: 2.3 のダブルバッファ待ちが 11〜14ms。perform(SET_BUFFER_COUNT,3) で 42→55fps（A§7）。
- **その他の効いた設定**（A§7）: 565 の窓で深度なし +6、早めの present +4、atest_zwrite +3。
  - tex16 と fbo565 は効果なし。
- **glReadPixels をやめる**: 197ms かかっていた。代わりにサーフェスのテクスチャをキャッシュする（A§9）。
- **記録なし**: RAM 使用量や OOM、ETC1/ATC の使用。

## 6. 風神録で最初に打つべき手
PC の最大 98MiB は、Go の上限 44.6MB（ELF 9.5MiB の場合）の 2 倍を超えています。中身はまだ調査中なので、どこを削るかは決め打ちしません。

1. **最初に計測を入れる**: 確保元つきの alloc ログ、面ごとの使用量・空き・最大連続、NEW_FAIL の即時 flush。
   - 根拠: 余裕が数十KB でも通るかどうかは運だった（台帳 L284）。死因は最大連続の不足（M8 L51）。PPSSPP の値は上限ではない（M8 L218）。
2. **起動宣言を固める**: MEMSIZE=1＋PSP_HEAP_SIZE_KB(-2048)＋ARK-5 の Extra Memory=Max。
   - 根拠: 800200D9（M7 L68）、ヒープ 13KiB 事件（M8 L71-73）。
3. **起動直後に大ブロックを確保し、タイトルと面で時分割する**。
   - 根拠: 大物 ANM の連続確保での落ち（M7 L75、L144、M8 L51）。
4. **大 ANM は前方トリムかメモステキャッシュにする**。
   - 根拠: title.anm は展開後 6.09MiB（ thdat -l の値）で、title01 と同じ種類の問題になる（B§9.4、T7 CHANGELOG）。
5. **テクスチャ**: 16bit を既定にしてスウィズルする。DXT は使わない。CPU 側のコピーを持たない。動的テクスチャはその場更新にする。
   - 根拠: M8 L136、B§29、B§30.2、M8 L237。
6. **ge4wrap で VRAM を 4MiB にする**: 上位に 3枚目のバッファ（272K）とよく使うテクスチャ、下位に立ち絵を置く（L239）。
7. **ホスト層は libGU/sceAudio の直叩きにし、SDL/PSPGL は持ち込まない**。
   - 根拠: harfbuzz だけで 1.3MB（B§2.1）。「Present が GE の描き終わりを保証する」前提に頼った作りで、トリプルバッファ化が 2 連敗した（M8 L113）。PSPGL を撤去したら 60 モード率が 79→94%（M8 L343）。
8. **ef0 での seek と極小 read の連打を避ける**。ME は音声だけに使い、eDRAM は使わない。
   - 根拠: ME 化はおよそ 110 版試して、勝てたのは音声だけ。

Xperia は初日から、変異シェーダ、バッファ3枚、565、glReadPixels なし、glBufferData 排除で始めます。RAM 使用量は記録が無いので実測してください。
